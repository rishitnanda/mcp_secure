1  Problem Statement
1.1  Why MCP Is a Security Blind Spot
MCP has become the de-facto standard for connecting LLMs to external tools. Over 5,000 community servers exist, yet — as the paper establishes — no formal security analysis of the protocol specification existed before January 2026. Existing developer tools treat MCP either as a simple HTTP proxy or as an open bridge, leaving three protocol-level doors wide open:

Vulnerability	Plain English Description
Least Privilege Violation	A server that declared only 'resources' capability during handshake can later call sampling/createMessage with no enforcement. The spec does not bind capability declarations to subsequent messages.
Sampling Without Origin Auth	Servers inject prompts using the 'user' role via sampling/createMessage. Tested MCP hosts (Claude Desktop, Cursor, Continue) show zero visual distinction — the user cannot tell if a prompt is theirs or was injected by a server.
Implicit Trust Propagation	In multi-server setups, a compromised Server A can embed instructions in its tool response that cause the LLM to invoke Server B, exfiltrate data, or persist malicious context. The spec defines no isolation boundary.
Shadow Tool Registration	A malicious server registers a tool named 'read_file' that shadows the trusted one. MCP clients merge tool lists blindly — there is no namespace protection.

Paper finding: With 5 concurrent MCP servers (1 compromised), attack success rate reaches 78.3% with a 72.4% cascade rate. This is your core motivation — put it front-and-centre in the README.

1.2  What Exists Already and Why It Isn't Enough
The paper surveys MCPSecBench (attack taxonomy, no mitigations), MCPGuard (runtime scanning), and ATTESTMCP (the protocol extension it proposes). None of these exist as a runnable, self-contained, open-source security suite. That is the gap this project fills.
    • MCPSecBench → taxonomy only, no enforcement
    • MCPGuard → commercial, cloud-dependent
    • Spotlighting / PromptArmor → prompt-level only, insufficient (paper shows prompt-only defences reduce cross-server ASR from 61.3% to 47.2%, vs ATTESTMCP's 8.7%)

2  Architecture Overview
The suite is a Dual-Layer Defense Chain. Every MCP tool call passes through both layers in sequence.

Layer	Component & Role
Layer 1 — Shield	MCP-Shield: protocol-aware JSON-RPC proxy. Intercepts, validates, and either blocks or forwards every tool call. Implements ATTESTMCP concepts.
Layer 2 — Box	MCP-Box: ephemeral Docker sandbox. Receives only pre-validated payloads from Shield. Executes code in an air-gapped container and returns stdout/stderr.
Cross-cutting	Async SQLite telemetry (WAL mode). Both components write audit logs non-blocking via aiosqlite + asyncio.create_task. A static admin dashboard reads these logs.

Design decision to lock in: Shield talks to Box over a local Unix socket or loopback HTTP — not over a real network — so Box never needs to be exposed externally. Document this explicitly; interviewers will ask.

2.1  Data Flow (Narrative)
1. AI client (Cursor, Claude Code, custom agent) sends a JSON-RPC 2.0 tools/call request.
2. MCP-Shield gateway parses the frame, validates the Pydantic schema, checks the capability certificate (ATTESTMCP), and runs the three-stage policy engine (regex → AST → namespace check).
3a. If blocked: Shield returns a structured JSON-RPC error (−32602 / −32601 / −32700) and writes a BLOCKED record to SQLite asynchronously.
3b. If passed: Shield constructs an execution context object and dispatches it to MCP-Box.
4. MCP-Box creates a one-shot Alpine container (network_mode=none, mem_limit=128m, 2 s watchdog). It captures stdout/stderr and forcibly removes the container in the finally block.
5. Box returns execution result to Shield. Shield forwards it to the AI client and logs the full lifecycle (duration, exit code, memory) to SQLite.

3  Project 1: MCP-Shield (Proxy & Governance Layer)
3.1  Core Objectives
    • Intercept JSON-RPC 2.0 frames over stdio and HTTP/SSE transports
    • Enforce capability attestation via signed certificates (ATTESTMCP)
    • Block shadow tool registrations by locking tool namespaces
    • Tag and consent-gate all sampling/createMessage calls
    • Validate code payloads with a three-stage policy engine (regex → AST → namespace)
    • Sanitize tool output to block indirect prompt injection before it reaches the LLM
    • Replay-protect SSE streams via HMAC-SHA256 + sliding nonce window
    • Log all events asynchronously to SQLite (WAL mode) without blocking the request path

3.2  Security Engines
A  Capability Attestation Validator
Implements ATTESTMCP Vulnerability 1 mitigation. On connection, Shield expects a capability_cert JSON block signed by a known CA (federated model: platform vendors act as CAs). If the server lacks a cert, Shield operates in Permissive mode (warn) or rejects outright (Strict mode) depending on config.

Open question for you: How will you generate and self-sign test certificates for your pytest suite? You need a lightweight CA fixture. Look at the Python cryptography library's x509 module — you can generate a self-signed CA in ~20 lines and sign server certs from it. This is important to implement early as everything else depends on it.

B  Sampling Interceptor & Origin Tagger
All sampling/createMessage requests are intercepted. Shield (i) prepends an origin tag to the message payload — [ORIGIN: server_id] [WARNING: server-generated, not user] — and (ii) pauses for explicit user consent before forwarding. This directly mirrors the paper's ATTESTMCP Origin Tagging design principle.

C  HMAC Message Integrity & Replay Protection
For HTTP/SSE transport: every JSON-RPC request must carry a mcpsec header containing server_id, timestamp, nonce, and HMAC-SHA256 signature. Shield maintains a sliding window of 1,000 nonces per server with a 30-second validity window (directly from the paper's design spec).

D  Three-Stage Policy Engine (policy.py)
Stage 1 — Regex Lexical Scan: Pre-compiled patterns against blacklisted strings. Examples: rm\s+-rf, chmod\s++x, /etc/passwd, nc\s+-e, curl.*bash.

Stage 2 — AST Parser: For code execution tools, the payload is parsed into a Python AST. The walker blocks: any ast.Import / ast.ImportFrom for restricted modules (os, sys, subprocess, socket, ctypes, urllib); calls to eval() / exec(); runtime attribute retrieval via getattr().

Stage 3 — Namespace Verification: Intercepts tools/list responses. Compares returned tools against shield_config.json's allowed list. Strips any tool attempting to shadow a protected name.

Critical implementation note: The AST check must be run BEFORE the payload is forwarded to MCP-Box. Even if Box is air-gapped, the AST check creates an evidence trail and blocks obfuscation attempts that might exploit Python internals. The example in your refined doc — getattr(globals()['__builtins__'], '__import__')('os').system('ls') — is exactly the kind of thing the AST walker catches that regex cannot.

E  Output Sanitizer (Indirect Injection Block)
Tool outputs (file reads, web fetches, DB queries) are intercepted before reaching the LLM context. If text matches injection signatures — lines starting with 'System:', 'Human:', or containing 'Ignore previous instructions' — the proxy replaces the block with a sanitized warning token.

3.3  Exception-to-JSON-RPC Mapping

Exception Type	JSON-RPC Code → Message
Pydantic ValidationError	−32602 Invalid Params → 'Schema validation failed: [field details]'
PolicyViolationException (regex)	−32602 Invalid Params → 'Security policy violation: Blocked sequence'
ASTValidationException	−32602 Invalid Params → 'Security policy violation: Restricted AST token'
json.JSONDecodeError	−32700 Parse Error → 'JSON parse error'
MethodNotFoundException (namespace lock)	−32601 Method Not Found → 'Method not found: [tool_name]'
asyncio.TimeoutError (from Box)	−32603 Internal Error → 'Execution timeout'
docker.errors.APIError (from Box)	−32603 Internal Error → 'Sandbox error'
CapabilityViolationException	−32601 Method Not Found → 'Capability not attested: [cap_name]'

3.4  Async Telemetry Pipeline (database.py)
    • SQLite opened on lifespan startup with PRAGMA journal_mode=WAL and PRAGMA synchronous=NORMAL
    • All log writes issued as asyncio.create_task() — never awaited on the hot path
    • aiosqlite.Error caught inside the background worker, printed to stderr, never propagates up
    • Schema: logs(id TEXT, timestamp REAL, method TEXT, payload TEXT, status TEXT, duration_ms REAL, exit_code INT)

Idea to add: Expose a /metrics endpoint on the FastAPI server returning counts by status (BLOCKED, TIMEOUT, SUCCESS, SANITIZED). This makes the admin dashboard non-trivial and gives you something to demo live.

4  Project 2: MCP-Box (Ephemeral Sandbox Engine)
4.1  Core Objectives
    • Accept only pre-validated execution contexts from MCP-Shield
    • Spin up a one-shot python:3.11-alpine container per code invocation
    • Enforce strict resource caps: network_mode=none, mem_limit=128m, nano_cpus=1_000_000_000
    • Kill any execution exceeding 2.0 s via asyncio.wait_for + asyncio.TimeoutError
    • Forcibly remove containers in a finally block regardless of outcome
    • Prune orphaned containers on startup via label-based Docker filter

4.2  Execution Flow
Step 1: Write the code string to a host-side temp directory (unique UUID-named folder).
Step 2: Create container with python:3.11-alpine image. Mount the temp folder to /workspace (rw). Root filesystem is read-only. No network interfaces active.
Step 3: Start the container inside loop.run_in_executor() to avoid blocking the asyncio event loop. Then await asyncio.wait_for(container.wait(), timeout=2.0).
Step 4: On success — capture container.logs(). On TimeoutError — call container.kill(). In both branches — finally block calls container.remove(v=True, force=True) and shutil.rmtree(temp_dir).
Step 5: Return structured dict {exit_code, logs, status, duration_ms} to Shield.

4.3  Why This Beats Commercial Alternatives
Dimension	MCP-Box vs. Commercial
Network dependency	MCP-Box: zero — runs on local Docker socket (unix:///var/run/docker.sock). E2B / Modal: cloud round-trip latency per call.
Default network posture	MCP-Box: network_mode=none by default — physically impossible to exfiltrate. Standard Docker: bridge driver active, internet reachable.
Cost at scale	MCP-Box: free (local). E2B: per-execution billing. Modal: compute credits.
Research reproducibility	MCP-Box: single docker-compose up, fully self-contained. Cloud tools require account setup, API keys.
Cold start	MCP-Box: sub-second with alpine base image cached locally. MicroVM (E2B/Firecracker): ~200ms+ cold start from scratch.

Honest limitation to document: MCP-Box uses OS-level containerisation (namespaces + cgroups), not hardware virtualisation (Firecracker/gVisor). A container escape in a real kernel vulnerability could affect the host. This is academically honest to state in your paper/README — and then argue the threat model: in a local dev context this is acceptable; in production, swap the Docker backend for a Firecracker executor. Acknowledging this shows maturity.

4.4  Daemon & Orphan Cleanup
    • Every container gets label mcp-box-sandbox=true at creation time
    • On MCP-Box driver startup: query client.containers.list(all=True, filters={'label':'mcp-box-sandbox=true'}) and kill+remove all matches
    • Read-only root filesystem prevents scripts from poisoning the alpine base image

6  Threat Model
Attack success rates (ASR) are sourced directly from the paper's PROTOAMP experiments across 847 scenarios, 5 MCP server implementations, 3 LLM backends.

Attack Vector	Root Cause in MCP v1.0	Mitigation Layer	Status
Capability Escalation (Vuln 1)	Capability declarations self-asserted at init; no message-level enforcement in MCP v1.0	Shield — Capability Attestation Validator rejects uncertified capability invocations	Covered
Sampling Injection (Vuln 2)	Server uses user role in sampling/createMessage; hosts show zero UI distinction (tested: Claude Desktop, Cursor, Continue)	Shield — Origin Tagger prepends server identity; consent gate before forwarding	Covered
Cross-Server Propagation (Vuln 3)	LLM context conflates outputs from all servers; no isolation boundary in spec; ASR 61.3% with 1 compromised server	Shield — Output sanitizer + user-prompted cross-server authorization	Partial
Shadow Tool Registration	Clients merge tools/list responses blindly; malicious server registers 'read_file' to hijack intent	Shield — Namespace lock strips non-whitelisted tools from list responses	Covered
Infinite Loop / Resource Bomb	Untrusted AI code runs while True or fork-bombs; locks host thread	Box — asyncio.wait_for(2s) + container.kill() + mem_limit=128m	Covered
Data Exfiltration via Network	Injected script parses .env or ~/.ssh and POSTs to attacker endpoint	Box — network_mode=none; physically no interface to reach internet	Covered
Indirect Prompt Injection	Tool reads a web page or file containing 'Ignore previous instructions'	Shield — Output sanitizer intercepts before LLM context injection	Covered
AST Obfuscation Bypass	getattr(globals()['__builtins__'], '__import__')('os').system('ls')	Shield — AST walker catches getattr + globals access pattern	Covered

What the suite does NOT cover (be honest in your paper): (1) Container escape via kernel exploit — Box uses OS namespaces, not hardware virtualisation. (2) A legitimately-certified server serving malicious content — attestation proves identity, not behaviour. (3) Social engineering to authorise a malicious server. (4) First-contact TOFU attacks where a new server never claims ATTESTMCP.

8  New Ideas & Extensions
8.1  Ideas Worth Adding (High Value, Low Effort)
    • shield_config.json hot-reload: Use watchdog (Python file watcher) to reload the policy config without restarting the gateway. Useful for live demos.
    • /metrics SSE stream: Push live stats (block rate, active containers, last attack type) as Server-Sent Events to the dashboard. One endpoint, impressive live demo.
    • Structured audit export: Add a CLI command that dumps the SQLite log to a signed JSON or PDF report. Shows you think about compliance workflows.
    • TOFU (Trust On First Use) pinning: First time a server connects without a cert, Shield records its public key. Any subsequent connection from the same server_id with a different key triggers an alert. Low cost, catches downgrade attacks.
    • Configurable trust levels per tool: In shield_config.json, allow execute_code to require Strict mode while read_file uses Permissive. Granular security policy is a real enterprise concept.

8.2  Ideas to Defer (High Effort, Lower Return for Now)
    • Full federated CA infrastructure: Interesting but massive. Use self-signed certs with your own CA for the project; note in the paper that production would use a federated model.
    • gVisor or Firecracker backend for Box: Better isolation than Docker but complex setup. Mention as a future work item — it shows you know the limitation.
    • LLM-assisted policy engine: Using Claude to detect injection patterns. Circular dependency (using an LLM to protect an LLM call) — interesting research question but out of scope here.

8.3  Critical Open Questions
Q1: How does Shield receive tool output for sanitization in stdio mode? The stdio proxy must buffer the full server response before forwarding — design this carefully or you will have a streaming race condition.

Q2: The consent mechanism for sampling/createMessage — what is the UX? In a CLI context, a blocking input() works. In an IDE integration, you need a push notification or a callback. Decide and document this before coding.

Q3: You listed shield_config.json as declarative tool namespace configuration. Will this work per-connection (different configs for different servers) or is it a global policy? Per-server config is more realistic but requires Shield to track which server each connection belongs to throughout its lifecycle.
